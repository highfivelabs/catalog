# Terraform providers: coverage, leverage and licence

Findings of 2026-11-09 for the builder, who asked: "is it worth drawing a
comparison directly to what terraform providers cover and don't? is there any
opportunity to leverage tf provider code to generate ours if their coverage is
better and we can nearly get that for free?" Two follow-ups are answered here
too: the builder's guess that provider coverage is "probably more like 80%
across each, and maybe higher for the programmatically managed and generated
ones (google + google beta)", and Magic Modules as a machine-readable source.

Everything below is generated by the scripts in `hack/terraform/` from the
pinned inputs, except the prose, the licence review and the two spike logs.
Per-repository files for the three coverage dashboards are in
`docs/terraform/<repo>/` ("Files for the dashboards").

## Summary

1. **Yes, the comparison is worth drawing, and it is cheap.** It is a new
   column, not a new schema (`docs/terraform/<repo>/terraform.csv`).
2. **The builder's 80% is right for AWS, about two thirds for Google, and a
   third for Azure**, counted as the share of an API resource's attributes
   that the Terraform provider has, for the resources it has at all
   ("within mapped resources" below). Against the whole API (every resource
   in the dashboards' denominators) it is lower, because Terraform has no
   resource for 40 to 77 percent of them.
3. **Platform foundation, attributes covered, Terraform (L2, see "Method")
   against Config Connector, ACK and ASO ("official") and against us:**

   | Cloud | Official | Ours beyond | `google-beta` / `aws` / `azurerm` | Terraform adds beyond official and ours |
   | --- | ---: | ---: | ---: | ---: |
   | Google Cloud | 38.8% | 0.4% | 59.9% (`google`: 59.0%) | +27.4 points |
   | AWS | 28.2% | 1.6% | 51.5% | +32.9 points |
   | Azure | 43.0% | 2.2% | 18.7% | +6.4 points (a floor, see "Method") |

4. **Terraform has every ranked foundation gap** of the three work queues
   except one row (Azure policy attestation), and partly four GCP rows and
   three Azure rows ("Foundation gaps against Terraform"). It is the better
   coverage source for AWS and Google Cloud, not for Azure.
5. **Leverage verdicts.**
   (a) Config Connector's Terraform mechanism: works (spike 2), but the
   vendored provider is 4.84.0, four majors behind 8.10.0, and loading it is
   the option our design already rejected. **No.**
   (b) Upjet providers (`crossplane-contrib`, Apache-2.0, released about
   monthly): the only path that gives real controllers for nearly free.
   **Yes for AWS** as an opt-in fourth provider type, **maybe for Google
   Cloud**, **no for Azure**. Needs the builder's decision (below).
   (c) A generator of our own from provider schemas: **no**; the CRD half
   is easy (4 seconds), the controller half is Upjet.
   (d) Benchmark and roadmap: **yes, now**, and **Magic Modules' YAML
   (Apache-2.0) is worth feeding to our scaffolder** for Google Cloud.
6. **Licence.** The providers are MPL-2.0 (file-level copyleft), Upjet and
   its providers Apache-2.0 with MPL libraries named in NOTICE, Magic Modules'
   resource YAML Apache-2.0, Terraform core BUSL (not needed: OpenTofu is
   MPL-2.0). Depending on or running Upjet providers is low risk; copying
   provider files into our tree is not. What needs a lawyer is in
   "Licence and risk".
7. **Decision for the builder:** is a Crossplane/Upjet provider type
   acceptable in Bundt's story of Kubernetes-native clouds, at least for AWS
   Organizations, IAM Identity Center, Control Tower and the security
   services? Details in "Recommendation".

## Method and error

`hack/terraform/export-schemas.sh` runs `tofu providers schema -json` for the
pinned providers on an offload VM and flattens every resource to its writable
attributes (`flatten.py`: required or optional, nested blocks and object
types to dotted paths with `[]` and `{}` as the dashboards write them).
`hack/terraform/analyze.py` then does, per cloud:

1. **Resource mapping.** A Terraform resource is mapped to the API resources
   of the dashboard's denominator by (in order): a hand list
   (`hack/terraform/overrides.csv`, 60 rows); for Google, Magic Modules' own
   statement of the API host and collection of each generated resource
   (`product.yaml` base URL, the resource `base_url`) against the Discovery
   path in the dashboard's `resources.csv` notes; for Azure, the
   `go-azure-sdk/resource-manager/<service>/<version>/<type>` package that the
   azurerm source imports (the package is the lower-case last segment of the
   ARM type); then name tokens plus attribute overlap. IAM add-ons
   (`*_iam_member`, `_binding`, `_policy`) map to nothing, as the dashboards
   do not count them as resources.
2. **Attribute match.** An API attribute counts as covered when a writable
   attribute of a mapped resource has the same name. **L1** compares the whole
   dotted path with case, separators, plurals and `properties` wrappers
   removed (`ipConfiguration.authorizedNetworks[].name` equals
   `ip_configuration.authorized_networks.name`). **L2** also accepts a match
   of the last two path segments, which catches providers that nest
   differently (`nodePools[].config.taints[].key` against
   `node_config.taint.key`). L1 is the floor, L2 the better estimate.
3. Numbers are joined with the dashboards' `covered_by` column
   (`official`, `ours`, `both`, `none`), so the overlap with official and with
   ours is exact for the attributes the mapping reaches.

**How far to trust it.**

- *Precision of L2*: 22 random attributes per cloud that L2 counts and L1
  does not (`hack/terraform/sample.py`, seed 7, platform foundation; drawn from a
  revision of the mapping before the Magic Modules and Azure SDK joins and the
  last overrides) were read by hand: Google 22 of 22 are the same attribute under a different
  nesting; AWS 22 of 22; Azure about 19 of 22 (the misses join a subnet's
  `properties.subnet.id` to association resources and a firewall rule group
  draft to the rule collection resources). So L2 overstates by roughly 0 to
  15 percent of the attributes it adds.
- *Recall of the resource mapping*, tested with resources Config Connector,
  ACK or ASO already cover (which nearly always have a Terraform
  counterpart): of the platform-foundation resources with an official kind,
  94 of 99 (Google), 47 of 55 (AWS) and 74 of 80 (Azure) have a mapped
  Terraform resource; over the whole denominator 541 of 736, 215 of 266 and
  179 of 294. So **the platform-foundation numbers are good to a few
  points; the whole-API numbers are floors, most of all for Azure**, where
  azurerm splits and renames ARM resources (DNS record types, rule
  collections, public IPs) and about a third of its 1108 resources are
  unmapped (listed with the reason in `docs/terraform/data/azure-azurerm.mapping.csv`).
- The dashboards say their own name matching is right for about 90% of
  fields. Both errors stack.
- "Covers" means the schema has the argument. Whether the provider acts on it
  correctly, or can read it back, is not measured.
- Resource counts differ by up to 3 from the dashboards (zero-attribute
  resources, resource variants such as `organizations.policies`); attribute
  totals agree with the dashboards' `categories.csv` for Google and AWS and
  are within 0.4% for Azure (4,692 against 4,675 in platform foundation).

### Where we beat Terraform, and where we trail it

"We" is official plus ours. Differences of 15 points or more on services with
at least 20 attributes, platform foundation and security-adjacent:

- **Google Cloud: we trail Terraform in total, and lead in three small
  places.** Terraform covers 26.6 to 27.4 points of platform foundation that
  we do not; we cover 6.7 that it does not (13.0 of the whole API). We lead
  on Binary Authorization (76% against 19%), Cloud Asset (100% against 35%)
  and reCAPTCHA Enterprise (74% against 54%); some of those are the mapping
  (the Terraform names are far from the API's) and need a second look.
  Terraform leads in `gkehub` (54% against 16%), `iam` (79% against 44%),
  `compute` and `container` (about +34 each), `accesscontextmanager`,
  `assuredworkloads`, `secretmanager`. Our own kinds (59 attributes beyond
  official) are nearly all also in Terraform (52 of 59): they are gaps the
  provider already closed.
- **AWS: we trail Terraform almost everywhere.** ACK has nothing for
  Organizations' policies, IAM Identity Center, Identity Store, Control Tower,
  Network Manager, Config, GuardDuty, Security Hub, WAF, Macie, Access
  Analyzer and Firewall Manager (0% official; 49 to 97% in Terraform). We lead
  in `eks` (82% against 58%), `ecr` (70% against 54%), `route53` (48% against
  24%, partly mapping: CloudFormation's `RecordSetGroup` has no counterpart),
  ACM (88% against 21%) and ACM Private CA (95% against 25%); the last two are
  probably mapping misses (the Terraform attribute names are far from the
  CloudFormation ones) and should be re-checked. 243
  attributes of ours beyond ACK, 164 of them also in Terraform.
- **Azure: we lead Terraform almost everywhere**, by large margins in AKS
  (`ContainerService` 83% against 23%), Application Insights and Monitor
  (`Insights` 77% against 38%), `Network` (38% against 12%), Key Vault, the
  container registry and Kubernetes configuration. Terraform leads only in
  Cost Management and Consumption (budgets and exports: 92% and 28% against
  0%), Azure Policy remediation and the Authorization service (policy and
  role resources). Our own kinds (501 attributes beyond ASO) are mostly not
  in Terraform (only 78).

## Magic Modules: what the Google providers are generated from

Google's providers are largely generated from Magic Modules' `mmv1` resource
YAML (`mmv1/products/<product>/<Resource>.yaml`, one `product.yaml` per
product), with Go resources written by hand under
`mmv1/third_party/terraform/`.

**Generated against hand-written** (`hack/terraform/export-mm.sh`: the
derived Terraform name of every YAML definition against the schema):

| | `google` | `google-beta` |
| --- | ---: | ---: |
| Resources in the schema | 1,396 | 1,516 |
| Generated, as resources (YAML definition) | 862 | 931 |
| Generated, as IAM policy, binding and member (YAML `iam_policy`) | 372 | 417 |
| **Generated, total** | **1,234 (88%)** | **1,348 (89%)** |
| Hand-written or not matched | 162 | 168 |

Of the 1,010 non-IAM `google-beta` resources, 911 (90%) are generated. The
split is a lower bound on generated (a few definitions derive a different
name). The hand-written 10% is not the long tail: it holds much of platform
foundation, for example `google_folder`, `google_organization_policy` and
`google_folder_organization_policy`, the project, folder and organization
logging sinks, bucket configs and exclusions, `google_organization_iam_custom_role`,
`google_organization_iam_*` and `google_folder_iam_*`, the service identities,
`google_compute_project_*`, shared VPC, router interface and peer, network
peering, `google_dns_record_set`, `google_compute_security_policy`, the
Bigtable and Dataproc resources. 182 hand-written resource files are in
`gcp.mm-handwritten-files.txt`. The generator cannot give a scaffolder
these; the Discovery documents and the provider schema must.

**As a machine-readable source for our scaffolder.** The 970 definitions
(959 not excluded) in 185 products, 29,218 property definitions, parsed in
`gcp.mm-resources.csv` and `gcp.mm-properties.csv`:

| Quirk the Discovery document leaves out | In Magic Modules | Count |
| --- | --- | ---: |
| Immutable fields (force replacement) | `immutable: true` on a property | 3,183 of 29,218 |
| Output-only fields | `output: true` | 6,254 |
| Required fields | `required: true` | 5,967 |
| Fields the API fills in when unset | `default_from_api: true` | 1,591 |
| Update masks | `update_mask: true`, per-field `update_mask_fields` | 561 resources, 62 fields |
| Update verb | `update_verb` (PATCH 656, POST 32, PUT 2, absent 269) | 959 |
| Long-running operations | `async` (type `OpAsync` 455, `PollAsync` 19 on the resource; many more inherit it from `product.yaml`) | product and resource |
| IAM policy, binding and member | `iam_policy` block (parent attribute, method names, beta) | 140 resources |
| URLs, create and update | `base_url`, `create_url`, `self_link`, `update_url` | all |
| Beta-only | `min_version: beta` | 59 resources, 606 properties |
| Cross-field rules | `conflicts`, `exactly_one_of`, `at_least_one_of` | 252, 490, 485 |
| Sensitive fields | `sensitive: true` | 215 |
| Product API host and versions | `product.yaml` `versions[].base_url` | 185 products |

What it does not carry: 506 of 959 resources (53%) have `custom_code`, Go
templates that encode behaviour the YAML cannot (encoders, decoders, pre-delete
steps, constants); 50 have `custom_diff`; the hand-written 10% are absent;
field types are Magic Modules' (`NestedObject`, `Enum`, `ResourceRef`), not
the API's, and descriptions are the provider's. It is the best machine-readable
statement of Google Cloud API behaviour that exists outside the clients
themselves, and it covers precisely the quirks a direct controller must get
right (immutability, which fields go in the update mask, which operations are
long-running). It does not replace the Discovery document: it is a
Terraform-shaped view of the API and omits whatever Terraform omits.
**Recommendation: feed it to the scaffolder as a second input beside
Discovery** (see "Recommendation"); for the first use, immutability, update
masks and async flags per resource are the high-value columns.

## Leverage paths

### a. Config Connector's own Terraform mechanism

*How it works.* A Terraform-based kind is: an entry in
`config/servicemappings/<service>.yaml` (the Terraform resource name, the kind,
`idTemplate`, `containers`, resource references, ignored fields); the CRD,
generated from the vendored provider's schema by `scripts/generate-crds`
(`generateTFBasedCRDs`); one line in `pkg/controller/resourceconfig/static_config.go`
(`DefaultController: Terraform`); the supported-GVK list and RBAC, generated.
The reconciler (`pkg/controller/tf`) runs the provider's SDKv2 resource
in-process with `krmtotf` translating KRM to Terraform state. Config
Connector at our pin has 743 kinds: 449 direct, 225 Terraform, 65 DCL and 4
IAM (`config-connector-extensions/docs/design.md`); upstream says everything
is migrating to direct.

*What it covers.* Only what the vendored fork has. The fork's CHANGELOG head
says **4.84.0 (Unreleased)** (2023); it registers 1,026 resources, against
8.10.0's 1,396 (`google`). `google_folder_service_identity` and
`google_organization_service_identity` are not in it. `google_compute_project_default_network_tier`,
`google_project_default_service_accounts` and
`google_organization_iam_custom_role` are, and Config Connector has no kind for
the first two.

*What loading it costs.* Spike 2: a 568 MB manager (91 s cold build on 16 vCPU, 15 s cached) with a 323 to 335 MB resident set at rest, 63 MB of provider source, a 684 MB Config Connector checkout. The design decision already
taken (`config-connector-extensions/docs/design.md` 2.1, option C) rejects
copying the Terraform family: it needs `krmtotf`, `servicemappings` and the
provider fork (61 MB of source, `go list -deps` pulls 91 Config Connector
packages through them), pinned to a fork with no patch series.

*Verdict: no for our repository.* The mechanism is real and tiny (spike 2),
and the cheap way to use it is to add the service mapping to Config Connector
itself as a patch in `patches/k8s-config-connector/`, but then the kind is
reconciled by a patched Config Connector manager, not upstream's, which gives
up the "install upstream unchanged, run ours beside it" shape; and the
provider underneath is 2023's. The only candidates it could add beyond
direct kinds are in the 4.84 set; every other gap needs a newer provider.

### b. Upjet-generated Crossplane providers

*State (read 2026-11-09).* Upjet (`crossplane/upjet`) is Apache-2.0, active
(last push 2026-11-06; v2.5.1 on 2026-09-30; the v1 line is still patched).
It generates CRDs, controllers and docs from a Terraform provider's schema
and runs the provider in one of three modes: Terraform CLI per reconcile
(Terraform 1.5.5, the last MPL release, from an `upbound/terraform` fork),
the SDKv2 resource in process (no CLI), or the Plugin Framework over protov6
(no CLI); `provider-upjet-aws` and `-gcp` wire all three include lists. The
community providers are `crossplane-contrib/provider-upjet-aws` (v2.9.0,
2026-10-08, built on hashicorp/aws 6.65.0), `-gcp` (v3.1.0, hashicorp/google
7.46.1), `-azure` (v2.8.0, azurerm 4.81.0) and `-azuread`; all Apache-2.0,
none archived, releases every one to three months (AWS: nine releases in the
last twelve), packages on `ghcr.io/crossplane-contrib` and proxied at
`xpkg.crossplane.io`. The upstream Terraform versions lag the registry: AWS
6.65.0 against 6.72.0, Google 7.46.1 against 8.10.0 (a major), Azure 4.81.0
against 5.13.0 (a major). The official Upbound repositories now redirect to these.
Microsoft ships no Crossplane provider; the old non-Upjet
`crossplane-contrib/provider-azure` is archived (2025).

*Resources.* Counting each kind once (every kind has a cluster-scoped CRD and
a namespaced `.m.` CRD): about 1,074 AWS, 432 GCP, 782 Azure, 40 Azure AD.
Per-service family providers (`provider-aws-organizations`,
`provider-gcp-cloudplatform`, `provider-azure-authorization`, ...) install
only that service's CRDs on top of a small `provider-family-*` config package.
`provider-aws-organizations` v2.9.0: 6 kinds (Account, DelegatedAdministrator,
Organization, OrganizationalUnit, Policy, PolicyAttachment; `v1beta1`), 12
CRDs; the image is 284 MB (compressed layers; `provider-family-aws` another
283 MB, `provider-azure-authorization` 119 MB, `provider-gcp-cloudplatform`
87 MB). `provider-gcp-cloudplatform`: 16 kinds, among them Folder, Project,
ProjectService, OrganizationIAMCustomRole, ProjectDefaultServiceAccounts,
`*IAMMember` for folder, organization and project; not the legacy
organization-policy resources, folder or organization IAM bindings or
policies. `management.azure.upbound.io` has ManagementGroup and its
subscription association; `authorization.azure.upbound.io` the policy
definition, set, assignments at three scopes and exemptions.

*Behaviour.* Readiness is conditions: `Ready` (after observe) and `Synced`,
plus `LastAsyncOperation` for the async create/update/delete path, as spike 1
shows. External names are configured per resource (`GetExternalNameFn`);
management policies (observe-only, import, late-initialise) are supported;
late initialisation fills `spec.forProvider` from the cloud's defaults only
when the management policies allow it; state is held in memory in the SDK
mode and rebuilt from `status.atProvider` plus annotations after a restart.
Drift is corrected on the next observe (spike 1). A resource that Terraform
moves from SDKv2 to the Plugin Framework can break its external-name
configuration until the provider is updated (for example
`provider-upjet-aws` issue 1725, `aws_s3_bucket_lifecycle_configuration`,
5.86.0); about 550 `@FrameworkResource` against 1,350 `@SDKResource` files in the
AWS provider means this is ongoing.

*Testing against emulators.* AWS: the ProviderConfig has `endpoint`
(`url.type: Static`, `source: Custom`, `services`, `hostnameImmutable`, the
signing fields) and the `skip_*` flags; the spike shows what it takes to point it
at moto (spike 1). GCP: the ProviderConfig has `credentials`, `projectID`,
`universeDomain` and no per-service endpoint, so mockgcp would need a
universe domain that serves all services, which mockgcp does not. Open issue
2213 (2026-08-26) reports S3 reads failing against custom S3 endpoints.

*What Bundt needs to treat these as a fourth provider type.* Bundt delivers
any Kubernetes objects and reads readiness from conditions, so the objects
themselves are deliverable as they are. The new work is (1) installing
Crossplane (two Deployments, 62 MB and 17 MB at rest, spike 1) and
the family providers as a Package of their own (`pkg.crossplane.io` objects
and a `DeploymentRuntimeConfig` for the cloud identity), (2) a ProviderConfig
per Target (credentials by Secret, IRSA or workload identity), (3) a
readiness rule for these kinds (`Ready` and `Synced`; `Synced=False` is a
blocking finding, and the cluster-scoped legacy kinds versus the namespaced
`.m.` kinds need a choice), (4) deletion policy (`Delete` or `Orphan`) and
management policies mapped from Bundt's, (5) the Package author's doc: the
spec is Terraform-shaped (`forProvider`, `initProvider`, references and
selectors) not ours.

*Licence.* Apache-2.0 with a NOTICE that names the MPL-2.0 libraries it
combines. The provider binaries embed the MPL-2.0 Terraform provider; the
crossplane-contrib packages are Apache-2.0 builds. Upbound's "official"
packages (`xpkg.upbound.io/upbound/...`) were commercially licensed builds
with paid access to older versions and, from Crossplane 2.0, a requirement to run
UXP; the Upbound package policy (v1.0.0, effective 2025-10-14) makes main
releases of the last twelve months free and the newest release always
available, and says the repositories are moving to `crossplane-contrib`.
**Use `crossplane-contrib`**, which is the free path with no Upbound
account.

*Verdict: yes for AWS; maybe for Google Cloud; no for Azure*, subject to the
decision on a Crossplane provider type. For AWS the gain is the largest of
any path (platform foundation 28% to 62% when Terraform is added; Organizations,
Identity Center, Identity Store, Control Tower, Network Manager and the
whole security-adjacent group go from none to covered) and the service family
packaging keeps the footprint to the services used. For Google Cloud, Upjet
adds up to 27 points of foundation but the GCP provider has no mockgcp path
and our direct-controller work already closes the ranked gaps one by one
with the quirks right; keep it as the fallback for a gap with no direct kind
in sight. For Azure the gain is under 7 points and ASO's generator is the
better road.

### c. Generating CRDs and thin controllers ourselves from provider schemas

Spike 2 shows the CRD half: the generator turns an 8-line service mapping
into the full CRD, with the provider's descriptions, required fields, and
conditions, in 4 seconds. The controller half is what Upjet is: an in-process
or CLI Terraform provider host, state, external names, async operations,
late initialisation, references, management policies, a test harness.
Config Connector's `krmtotf` and Upjet's `pkg/controller` are years of work
each. Doing it ourselves would give Bundt-native conventions
(`resourceID`, the knobs of `config-connector-extensions/docs/design.md`)
and one runtime, but it competes with the direct controllers we write
already (about a session per kind) and takes on the provider-plugin
protocol. **No.** It beats (a) and (b) only if Crossplane is unacceptable
and gaps remain after the direct controllers; revisit at that point. A cheaper
middle road exists for Google: generate the *direct* controller scaffolding
(types, mapper, identity, immutability, update masks, async) from Discovery
plus Magic Modules (below).

### d. Terraform as a benchmark and roadmap, with no code leverage

This is what the repositories already do ("read, not copied"). It gets sharper
with this document: the schemas give an exact, attribute-level list per
resource of what a Terraform user has and we do not, ranked by the module
need in the catalog. **Yes, now**, with the files in `docs/terraform/`.

## Licence and risk

*Providers.* `hashicorp/terraform-provider-aws`, `-google`, `-google-beta`,
`-azurerm`, `-azuread` and `Azure/terraform-provider-azapi` are all
MPL-2.0 (GitHub API, 2026-11-09); so are `terraform-plugin-sdk` and
`terraform-plugin-framework`. No relicensing was found after IBM completed its
acquisition of HashiCorp (2025-02-27). Terraform core is BUSL 1.1 since 2023
(licensor IBM, change licence MPL-2.0 four years after each release; the
additional use grant permits production use that does not offer a competing
hosted or embedded product); OpenTofu, the Linux Foundation fork, is MPL-2.0
and is what this work used (`tofu providers schema -json` needs no Terraform
core). Upjet's CLI mode runs Terraform 1.5.5 from an MPL fork, the last
MPL release.

*What the three ways of using it imply.*

| Way | Implication |
| --- | --- |
| **Reading** schemas, docs, behaviour (what we do now, and the data in this PR) | Facts about an API's attributes are not the provider's expression; low risk. The attribute lists in this PR are derived from the schemas, not copied code. |
| **Depending on or running** a built provider (Config Connector, Upjet providers, our manager if it loaded the fork) | MPL-2.0 is file-level copyleft: the provider's own files stay MPL and their source must be available when we distribute a binary containing them; code that merely uses it need not be MPL. Running `crossplane-contrib` packages that others build and distribute puts the distribution duty on them. Redistributing our own image that embeds the fork would put it on us (a notice and a source offer; `config-connector-extensions` already lists the Terraform packages in `NOTICE`). |
| **Copying** provider files into our tree, or committing generated code that includes provider-authored text (descriptions, validation messages) | Those files are MPL; modifications to them must stay MPL, and the repository would carry two licences. Avoid, or keep strictly separate. |
| **Generating** CRDs from the schema (a), (c) | The schema's field names and types are interface facts; the description strings are provider-authored text, and generated output that embeds them is where a lawyer should look. Config Connector and Upjet do this today under Apache-2.0 with MPL notices; neither project, nor HashiCorp, states a position that we found. |

*Registry terms.* The OpenTofu registry (`registry.opentofu.org`, Apache-2.0
software) served every provider download here. HashiCorp's Terraform Registry
terms of service were not retrievable (the page renders client side); our
runs do not use `registry.terraform.io` for downloads (only its public
version API for the pins). Reading them is on the list below.

*Packaging.* Use `crossplane-contrib` and not Upbound's official packages
(commercial licence on the published builds; paid access to older versions;
UXP from Crossplane 2.0 for the official line).

*Needs a lawyer:*

1. Whether schema-derived CRDs that carry provider description text, and
   Upjet-generated code, create MPL obligations for us if we generate and
   publish them (path c, or a scaffold that copies descriptions).
2. Whether shipping a Bundt release that installs `crossplane-contrib`
   images by reference is clean, and what a mirror of those images (for an
   air-gapped customer) triggers.
3. Whether using the OpenTofu registry as the provider source is clean for
   customers, and what the HashiCorp registry terms (not read) restrict about
   the provider binaries.
4. BUSL: only if a customer path ever runs Terraform core 1.6 or later
   inside our product; the recommendation does not.
5. The Magic Modules YAML (Apache-2.0) is clean to read and transform with
   attribution; the file mix in `mmv1/third_party/terraform` (MPL) is not
   for the scaffolder.

*Risk beyond licences.* Upjet lags the Terraform registry by weeks to
months and the AWS provider's SDKv2-to-Framework moves break
resource configuration from time to time; Crossplane 2 changed the managed
resource scope (cluster to namespaced) and Upbound's own distribution is a
separate product; image sizes are large (284 MB for six Organizations kinds);
and these kinds bring Terraform's conventions (`forProvider`, references)
into Bundt's Package authors' hands.

## Spikes

Run on offload Spot VMs (`hack/terraform/spikes/`); logs and artifacts are in
`docs/terraform/spikes/`.

### Spike 1: AWS Organizations through an Upjet provider against moto

*Setup* (`hack/terraform/spikes/aws-organizations/run.sh`, an offload Spot VM,
`e2-standard-8`): kind v0.33.0 with node image v1.32.2; Crossplane 2.4.3 (Helm);
`xpkg.crossplane.io/crossplane-contrib/provider-aws-organizations:v2.9.0`
(its dependency `provider-family-aws` v2.9.0 is pulled by Crossplane), run with a
`DeploymentRuntimeConfig` that sets `--poll=20s --debug`; moto 5.2.5 as a
container on kind's Docker network; the organization and the SCP policy type
seeded through boto3 (`CreateOrganization`, `EnablePolicyType`); a
`ProviderConfig` with a static endpoint, `source: Custom`,
`services: [organizations]`, `signingRegion: us-east-1`, fake credentials and
the four `skip_*` flags. A `Policy` (type `SERVICE_CONTROL_POLICY`) is created,
updated (content and description), changed out of band, and deleted; moto is
read independently with boto3 after each step.

*What worked.* All of it, on the second attempt:

| Step | Result |
| --- | --- |
| `kind create cluster` | 71 s |
| Crossplane install | 13 s |
| Provider and its family dependency `Healthy` | 21 s with the images on the node; 43 to 51 s in the earlier runs (image pull) |
| Create `Policy` to `Ready=True` | 10.9 s (an earlier run without `--debug` and the poll override: 3.8 s) |
| Update content and description, visible in moto | 1.4 s (earlier run: 1.5 s) |
| Change the description in moto, provider puts it back | 14.1 s with `--poll=20s`; with the default poll interval, no correction within 90 s (earlier run: the default is 10 minutes, so drift correction is slow unless the interval is lowered) |
| Delete, object gone | 14.2 s (earlier run: 0.2 s) |

`moto-after-update.json` shows the new content in moto, and
`moto-after-delete.json` only the AWS-managed `FullAWSAccess`. Conditions on
the object after the update: `Ready=True` (`Available`), `Synced=True`
(`ReconcileSuccess`, with `observedGeneration`), `LastAsyncOperation=True`
(`Success`); `status.atProvider` carries `arn`, `id`, `content`,
`description`, `type` and the Crossplane tags (`crossplane-kind`,
`crossplane-name`, `crossplane-providerconfig`), which the provider adds to
the SCP itself.

*Resource usage* (`crictl stats` in the kind node, `stats.txt`): Crossplane
62 MB and its RBAC manager 17 MB; **each of the two provider pods
(`provider-aws-organizations`, `provider-family-aws`) used 314 to 390 MB
at rest and 470 to 512 MB after a create** (with `--debug`), CPU about 125%
of one core while starting and under 1% idle; images 284 MB and 283 MB
(compressed layers `3f3905e0`, `6768c06a`), 23 MB for Crossplane. So **about
1 GB of memory and 570 MB of images to manage six Organizations kinds**.
Neither provider pod had resource requests or limits set.

*What broke or cost time.*

1. **First attempt: the endpoint override did nothing, and the requests went
   to real AWS.** The first ProviderConfig had `endpoint.url.type: Static`
   and `hostnameImmutable: true` but no `source: Custom` or `services`. The
   provider ignored it (no error, no warning on apply), signed requests with
   the fake credentials and sent them to the public Organizations endpoint,
   which answered `UnrecognizedClientException` (`attempt1/`). Nothing could
   be created. A mistyped endpoint block is therefore a way to send
   credentials, fake or real, to the real API; a Bundt Package for these
   providers should set the whole block and check it.
2. The ProviderConfig CRD silently accepts unknown or misplaced fields.
3. Benign conflicts in the provider log: `Async update callback failed ...
   the object has been modified` after an update and after a delete (the
   status write loses a race with the next reconcile; the operations had
   succeeded).
4. Not exercised: the `Organization`, `OrganizationalUnit`, `Account`,
   `PolicyAttachment` and `DelegatedAdministrator` kinds, references between
   them, late initialisation and management policies. moto's Organizations
   needs the organization to exist first, so the `Organization` kind was
   not used. Real AWS behaviour (SCP size limits, propagation, the
   organization-management-account call path) cannot be checked without
   credentials.


### Spike 2: one GCP foundation gap through Config Connector's Terraform route

*Mechanism, from the code* (Config Connector at the pin of
`config-connector-extensions`, `672414b8`): a Terraform-based kind is the
Terraform resource's name, a kind name, an ID template and its containers in
`config/servicemappings/<service>.yaml`, plus one line in
`pkg/controller/resourceconfig/static_config.go`. `scripts/generate-crds`
reads the vendored provider's schema and writes the CRD; `pkg/controller/tf`
(`Add(mgr, crd, provider, smLoader, defaulters, jitter)`) reconciles it with
`krmtotf` over the in-process SDKv2 resource. Target: **`ComputeProjectDefaultNetworkTier`**
(`google_compute_project_default_network_tier`, foundation row 1): in the fork,
no Config Connector kind, one required field. The best-chance rows were
checked first: `google_organization_iam_custom_role` (row 3) is already
reachable through `IAMCustomRole`; `google_folder_service_identity` and
`google_organization_service_identity` are not in the fork at all
(4.84.0); `google_project_default_service_accounts` is in the fork, needs
more IAM than the test account has.

*What was built* (`hack/terraform/spikes/kcc-tf-kind/`, patch in
`patch.diff`: 9 added lines in two files):

| Step | Result |
| --- | --- |
| Fetch Config Connector at the pin | 21 s, 684 MB checkout, provider fork 63 MB |
| Build `generate-crds` | 90 s cold on 16 vCPU, 8 s with the Go cache; 235 MB binary |
| Generate the CRDs | 3.9 s for all 329 Terraform-family CRDs; the new one is 115 lines, `spec.networkTier` required, with the provider's description (`crd.yaml`) |
| Build the Config Connector manager | 91 s cold, 15.5 s cached; **568 MB binary** (all three reconciler families and the fork) |
| Run it (host process, kind cluster, ADC of `cce-live-tests`) | starts; the registration controller picks the CRD up and starts `computeprojectdefaultnetworktier-parent-controller`; **RSS 323 to 335 MB** at rest with five CRDs installed |
| Create the object | the TF controller reads live state and calls `SetDefaultNetworkTier` within a second |

*What did not work, and why.* The call was refused: `googleapi: Error 403:
Required 'compute.projects.setDefaultNetworkTier' permission for
'projects/hfl-dev-514205', forbidden` (`after-create.yaml`, `Ready=False`,
`reason: UpdateFailed`). The test service account `cce-live-tests` has
`compute.networkAdmin`, `compute.securityAdmin`, `compute.instanceAdmin.v1` and
no role that includes that permission (for example `roles/compute.admin`). I
did not widen it. So the kind is built, generated, registered and reconciled up
to the cloud call; **the live write is one IAM role from proven**, and the
project was left as found (`defaultNetworkTier` `PREMIUM` before, after update
and at the end). Deleting the object then hung on its finalizer in the
throwaway cluster, which was destroyed with the VM.

Two things the manager needed that the documents do not say: the operator's
`ConfigConnector` and `ConfigConnectorContext` CRDs must exist, even if no
object does (the registration controller reads them at start-up); and without
Config Connector's mutating webhook the object needs
`cnrm.cloud.google.com/project-id` itself (the namespace annotation is copied
by the webhook, not by the controller; the first attempt failed with `no value
found for annotation cnrm.cloud.google.com/project-id`).

*What it says.* The route is real and small: minutes of work for the
YAML and the table line, a CRD that is correct for the 4.84 schema, a
controller that needs no code. Its limits are all in what stands under it: a
2023 provider (1,026 resources against 1,396 in `google` 8.10.0, missing two of
the four hierarchy resources the row names), a 568 MB manager with a 330 MB
resident set, and the choice, already made, not to bring the Terraform family
into our manager. To use it as Config Connector does, the patch belongs in
`patches/k8s-config-connector/` and the kind in Config Connector's group, run
by a manager we build.


## Recommendation

Per cloud, in order:

1. **All three clouds, now (days):** add Terraform to the coverage
   dashboards from `docs/terraform/<repo>/` (below). It costs nothing and it
   makes the queue honest: the foundation rows Terraform has and the 6.7 (GCP),
   11.2 (AWS) and 33 (Azure) points of platform foundation we have that
   it does not.
2. **Google Cloud:** keep building direct controllers down
   `foundation.md`; read Terraform and Magic Modules for behaviour, as now.
   Add Magic Modules' `mmv1/products/**` YAML (Apache-2.0) as a second
   scaffolder input beside Discovery, first for immutability, update masks,
   async flags, IAM shape and the beta marker per resource. Do not load the
   Terraform fork into our manager (4.84.0, 568 MB manager in the spike).
   Keep Upjet GCP as a fallback only.
3. **AWS:** if the builder accepts a Crossplane provider type, install
   `provider-aws-organizations` first (F01, where ACK has nothing for SCPs),
   then `ssoadmin`, `identitystore`, `controltower`, `networkmanager`, and the
   security group (`guardduty`, `securityhub`, `config`, `waf*`), in that
   order, as one Package kind of provider alongside ACK. Write our own ACK
   kinds only for what is small and where the ACK controller is the better
   fit (we already lead in EKS, ECR, KMS). This closes 33 points of platform
   foundation and 60 of the whole API at the price of one runtime.
4. **Azure:** ASO's generator remains the road. Terraform adds 6.4 points of
   platform foundation (Cost Management, Consumption, Azure Policy
   remediation, a few Authorization resources) and we lead almost everywhere
   else; `azapi` as a generic fallback is not worth a runtime.

*Dashboard integration, without changing the shared CSV schemas.* One new
file pair per repository, shaped for `docs/coverage/`:

- `terraform.csv`, one row per (service, provider): `service`, `provider`,
  `category`, `resources_total`, `resources_terraform`,
  `resources_terraform_beyond_official_and_ours`, `attributes_total`,
  `attributes_terraform_l1`, `attributes_terraform_l2`, `pct_terraform_l1`,
  `pct_terraform_l2`, `attributes_official_and_terraform`,
  `attributes_ours_and_terraform`, `attributes_terraform_only`,
  `attributes_official_or_ours_without_terraform`,
  `pct_official_ours_terraform_union`, `pct_terraform_within_mapped_resources`.
  Keyed by the same `service` values as `services.csv`.
- `terraform-resources.csv`, one row per (resource, provider), keyed by the
  same `service` and `resource` values as `resources.csv`: the mapped
  Terraform resources and the per-resource counts, so a reader can see which
  resources the match relied on.

The bar beside official (blue) and ours (green) is `pct_terraform_l2`; draw it
as a separate bar with the L1 value as its lower tick, and say beside it
that it is an estimate with the error of "Method and error". For Google, two
bars (`google`, `google-beta`) or the `google-beta` one alone, as it differs
by under a point. For Azure, `azurerm` only, with a note that `azapi` is
generic.

*Decisions for the builder.*

1. **Is a Crossplane/Upjet provider type acceptable in Bundt's story of
   Kubernetes-native clouds?** It is Kubernetes-native (CRDs, conditions,
   no CLI in the SDK mode), but it is a second control-plane runtime and its
   objects are Terraform-shaped. A yes gives AWS its largest step; a no
   leaves AWS to ACK plus our kinds, with the Terraform data as a roadmap.
2. Whether the lawyer review in "Licence and risk" should happen before or
   after the first AWS provider is adopted.
3. Whether Magic Modules' YAML should become a scaffolder input for Google
   Cloud (recommended).
4. Whether to re-check `foundation.md` item 3 (organization custom roles)
   against a real organization.
